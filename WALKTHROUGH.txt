HOW TO EXPLAIN THIS CODEBASE — READ THIS WHILE TALKING TO THE REVIEWER
========================================================================

Say this first (one line, sets the frame):
"Everything runs locally — no cloud APIs. Ollama serves the LLM and embeddings,
Qdrant stores document vectors, Postgres stores the business data, FastAPI is
the backend, Streamlit is just a test UI."


STEP 1 — WHAT STARTS FIRST (docker compose up)
------------------------------------------------
Say: "docker-compose.yml brings up 5 containers: postgres, qdrant, ollama,
my api, and a streamlit ui. The api container's Dockerfile runs
`uvicorn app.main:app`, so app/main.py is the very first file of MY code
that executes."

File order at startup:
  1. app/main.py
       - builds the FastAPI app
       - registers 3 routers: health, chat_routes, document_routes
       - wires app/starter.py's `lifespan` function to run on startup
  2. app/starter.py -> lifespan()
       - on startup, spins up a background thread that calls ingest_directory()
       - this auto-ingests every file in data/documents/ into Qdrant so the
         app has something to answer from immediately, without blocking
         the server from becoming ready
  3. app/config/settings.py
       - loaded the moment anything imports it; reads every setting from
         environment variables (pydantic-settings), not from code

Say: "So by the time the server says it's ready, my documents are already
being embedded and indexed in the background."


STEP 2 — WHAT HAPPENS WHEN A USER ASKS A QUESTION (POST /chat)
------------------------------------------------------------------
Say: "A chat request hits app/routes/chat_routes.py. That's the entry point
for every question."

Order of execution for one chat request:
  1. app/routes/chat_routes.py -> chat()
       - cleans the message (app/utils/security.py -> sanitize_message)
       - pulls this session's past turns from ConversationStore (in-memory,
         thread-safe, bounded — oldest sessions/turns get evicted)
       - calls graph.invoke(...) — this is where my LangGraph pipeline runs
  2. app/agents/chat_agent.py -> build_graph()
       This is THE core of the app — a LangGraph state machine with 4 steps:
         a. condense   -> app/agents/condense.py
                          rewrites follow-up questions ("and sick leave?")
                          into standalone questions using chat history.
                          Only runs if the question actually needs history.
         b. route      -> app/services/routing_service.py (rules first)
                          then app/agents/chat_agent.py's LLM router (fallback)
                          Decides: "document" (RAG), "database" (SQL), or "both"
         c. rag / sql  -> runs one or both of:
                          - app/repository/vector_store.py -> search()
                            (embeds the query via Ollama, searches Qdrant,
                            reranks with app/services/retrieval_service.py)
                          - app/agents/sql_agent.py -> run_sql_agent()
                            (LLM writes SQL -> app/tools/sql_validator.py
                            checks it's a safe SELECT -> runs against Postgres
                            as a read-only role, logs every attempt)
         d. answer     -> the LLM writes the final answer using whatever
                          context (document chunks / SQL rows) came back
  3. Back in chat_routes.py:
       - saves this turn into ConversationStore
       - builds the HTTP response (answer, sources, sql info, session_id)

Say: "So one question can trigger retrieval, SQL, or both, in parallel —
LangGraph fans out to both branches and then joins them before the final
answer step."


STEP 3 — WHERE DOCUMENTS COME FROM (POST /documents/ingest or startup)
----------------------------------------------------------------------
Say: "Ingestion is the same code path whether it's startup auto-ingest or
a manual upload."

  1. app/routes/document_routes.py (file upload) OR app/starter.py (startup)
  2. app/services/document_service.py
       - loads the file (pdf/docx/txt/md), splits it into chunks, keeping
         section/heading metadata
  3. app/repository/vector_store.py -> ingest_file()
       - embeds each chunk via Ollama (app/llms/ollama_client.py)
       - upserts into Qdrant with all the metadata (filename, section,
         heading, chunker_version, etc.)


STEP 4 — THE THREE SAFETY LAYERS FOR SQL (if asked "how is SQL safe?")
------------------------------------------------------------------------
Say: "Three independent layers, so no single point of failure lets the
model write to the database or see data it shouldn't."
  1. app/tools/sql_validator.py — parses the LLM's SQL with sqlglot and
     rejects anything that isn't a single SELECT on an allowed table.
  2. Database role — the query runs as `assistant_ro`, a Postgres role
     that only has SELECT privileges, ever.
  3. Per-request guardrails — `conn.read_only = True` and a statement
     timeout, set fresh for every single query.


IF ASKED "WHICH FILE SHOULD I LOOK AT FIRST?"
------------------------------------------------
Say exactly this, in this order:
  1. app/main.py            (the entry point — everything starts here)
  2. app/routes/chat_routes.py   (the main feature — ask a question)
  3. app/agents/chat_agent.py    (the actual LangGraph pipeline)
  4. app/agents/sql_agent.py OR app/repository/vector_store.py (whichever
     they want to dig into — SQL path or document path)
  5. app/tools/sql_validator.py  (if they care about safety/security)


ONE-LINE SUMMARY TO OPEN WITH
------------------------------
"A FastAPI backend wraps a LangGraph pipeline with three agents — a
condenser, a router, and an answerer — that decide per question whether
to search documents in Qdrant, query Postgres through a validated
read-only SQL agent, or both, then merge everything into one answer."
